# Retail Revenue, Customer Retention, and Product Performance Analysis with PostgreSQL

An end-to-end SQL analytics project for a fictional UK online retailer selling
everyday household products. It covers schema design, data-quality testing,
reusable metric views and ten business analyses, all written in PostgreSQL.

> **All data in this repository is synthetic.** It was generated by a script in
> this repo and does not represent real customers, real products or any real
> company's performance.

---

## Business problem

The retailer wants to understand:

1. How orders, gross sales, discounts, returns and net sales change month to month
2. Which categories and products drive net revenue
3. Average order value, and how it varies by month and category
4. What share of customers buy again
5. How retention differs by first-purchase cohort
6. Which customer groups score highest on recency, frequency and monetary value (RFM)
7. How discounts relate to order value and net revenue
8. Which products sell well but are returned often
9. How sales differ by channel, region and customer segment
10. Which data-quality issues could affect these conclusions

## Tools and skills demonstrated

- **PostgreSQL:** schema design with primary keys, foreign keys, CHECK constraints and indexes, plus bulk loading with `\copy`
- **SQL techniques:** CTEs, joins, aggregation, CASE, `FILTER`, subqueries, and window functions (LAG, RANK, DENSE_RANK, NTILE, PERCENT_RANK, running totals, moving averages)
- **Advanced grouping:** `GROUPING SETS`, `ROLLUP`, `generate_series`, `percentile_cont`, `CORR`
- **Data quality:** 44 automated checks covering duplicates, missing values, invalid dates, orphans, implausible values, and payment, return and status consistency
- **Analytics:** KPI definition, cohort retention, RFM segmentation, return analysis, and careful reading of correlation versus causation
- **Python (standard library only):** deterministic synthetic data generation
- **Git and documentation:** data dictionary, ER diagram, reproducible setup

## Data provenance

All records are produced by `scripts/generate_data.py` with a fixed random seed
(default `42`). The generator's business rules include seasonality, segment
behaviour, promo effects, return rates and a 2025 price increase. These rules
are listed in [`data/README.md`](data/README.md). Any pattern the analysis finds
that matches one of those rules is a property of the simulation, not a
discovery. A small number of data-quality problems are injected on purpose so
the quality checks have real issues to detect.

## Schema overview

Six tables in a dedicated `retail` schema:

| Table | Grain | Key relationships |
|---|---|---|
| customers | one row per customer | — |
| products | one row per product | — |
| orders | one row per checkout | → customers |
| order_items | one row per product line | → orders, → products |
| payments | one row per payment attempt | → orders |
| returns | one row per return request | → order_items |

See [`docs/er_diagram.md`](docs/er_diagram.md) (Mermaid) and
[`docs/data_dictionary.md`](docs/data_dictionary.md).

### Revenue definitions

| Term | Definition |
|---|---|
| Sales scope | `completed` orders dated 2024-01-01 to 2025-06-30 that have at least one line. Cancelled and pending (unpaid) orders are excluded. |
| Gross sales | quantity × unit_price, before discounts and returns |
| Discount amount | discount applied to order lines |
| Checkout value | gross sales − discounts |
| Refunded returns | refunds on `refunded` returns, capped at each line's checkout value |
| **Net sales** | **gross sales − discounts − refunded returns** |
| Order count vs item count | distinct orders vs total units |
| AOV | checkout value ÷ orders (net AOV is also reported) |

Refunds are attributed to the month of the original order. A partially returned
line keeps its sale minus the refund. A fully returned line nets to £0, but its
order still counts as an order. All definitions live in one place,
`sql/04_views.sql`.

## Setup and run

**Requirements**

- PostgreSQL 14 or later, with `psql` available on your PATH. On Windows, the
  EDB installer includes pgAdmin and SQL Shell (psql).
- Python 3.8 or later. No extra packages are needed.

**1. Get the code and generate the data**

```bash
git clone https://github.com/bhavikdata/retail-sql-analytics.git
cd retail-sql-analytics
python scripts/generate_data.py          # Windows: py scripts\generate_data.py
```

This writes six CSV files to `data/` and prints row counts plus the IDs of
the deliberately injected data issues. Use `--seed N` for a different but
reproducible dataset.

**2. Create a database**

```bash
createdb retail_analytics                # add -U postgres if required
```

**3. Run the SQL scripts in order** (still from the repository root, because
`\copy` paths are relative to where `psql` starts)

```bash
psql -d retail_analytics -f sql/01_create_schema.sql
psql -d retail_analytics -f sql/02_load_data.sql
psql -d retail_analytics -f sql/03_data_quality_checks.sql
psql -d retail_analytics -f sql/04_views.sql
psql -d retail_analytics -f sql/05_analysis.sql
```

To save the output of a script to a file:

```bash
psql -d retail_analytics -f sql/05_analysis.sql -o reports/analysis_output.txt
```

**4. Verify.** The final query in `02_load_data.sql` prints row counts; compare
them with `data/README.md`. The final query in `04_views.sql` is a
reconciliation. Its expected totals (for seed 42) were computed independently
from the CSVs in Python. For example, net sales should be £114,204.50 across
2,307 orders. Every check in `03_data_quality_checks.sql` should show `pass`
or `known issue`.

Re-running from step 1 at any point rebuilds everything. Script 01 drops and
recreates the `retail` schema.

## Findings

Results from running the full pipeline on PostgreSQL 16 with seed 42. **These are
results on synthetic data**: they describe the simulation, not a real business.
Full detail for all ten analyses is in [`reports/findings.md`](reports/findings.md),
and the raw query output is in [`reports/analysis_output.txt`](reports/analysis_output.txt).

- **Monthly trend:** net sales were £114,204.50 across 2,307 completed orders,
  peaking in November 2024 (£10,908.65). The share of net sales from returning
  customers rose from 37% in the first six months to 61% in the last six.
- **Product concentration:** 26 of 45 products make up 80% of net sales, and the
  Cordless Handheld Vacuum alone contributes 15.4%.
- **Retention:** 62% of customers ordered again (premium 75%, budget 53%).
  RFM champions and loyal customers are 28.5% of customers but generate 54% of
  net sales.
- **Returns:** the overall unit return rate is 4.8%, but Wireless Earbuds (32.6%)
  and the Cordless Handheld Vacuum (21.1%) combine high sales with high returns.
- **Discounts:** discounted orders have larger baskets before the discount but
  slightly lower checkout value (£52.50 vs £54.91), and the pattern is not
  consistent across segments. This is an association only, not evidence that
  discounts cause higher or lower revenue.

**Validation:** row counts match `data/README.md`, the reconciliation in
`04_views.sql` matches the totals computed independently in Python, and all 44
data-quality checks return `pass` (37) or `known issue` (7). The known issues
affect less than 1.3% of net sales, so the headline results are not sensitive
to them.

## Limitations

- **Synthetic data:** results describe generator rules, not real behaviour.
- **Growth artefact:** every customer signs up inside the window, so early
  months have few customers and growth partly reflects base build-up.
- **Late returns:** returns received after 2025-06-30 are missing, which
  flatters recent months.
- **Correlation only:** discount results show association, not causation.
- **Judgement calls:** RFM segment rules, return-rate flags (1.5× overall,
  30+ units) and discount bands are choices, not standards.
- **Out of scope:** no shipping, tax, or inventory data; `unit_cost` is not yet
  used for margin.
- **Performance:** the SQL was written for PostgreSQL 14+ and has been run
  end to end on PostgreSQL 16. It has not been performance-tuned for large
  volumes.
